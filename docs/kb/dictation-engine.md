# 听写引擎

系统最复杂、最容易做错的部分。改这里之前务必读完——**规则之间互相牵制，改一处不看另一处必出 bug**。

## 两个必须严格区分的概念

| 概念 | 归属 | 定义 |
|---|---|---|
| **关键词**（key words） | **句子**的静态属性，导入时预计算 | 该句所有**实词** ∪ 该句中属于**高危同音组**的词 |
| **考察词**（tested words） | **本次作答**的属性，运行时确定 | 本次实际要求用户产出的词 |

```
候选词池 = 该句关键词 ∪ 该句中出现的用户历史错词
```

**不要把这两个词混用。** 轻档下两者不相等（只挖 3-5 个空），混用会让"只有关键词参与计分"这句话产生歧义，字段名也是按这个区分来的（`sentences.key_words_json` vs `attempts.tested_words_*`）。

## 高危同音组（没有它核心能力直接失效）

`their`/`there`/`they're`、`its`/`it's`、`than`/`then`、`to`/`too`、`your`/`you're`、`were`/`where`/`we're`、`of`/`off`、`whose`/`who's`、`weather`/`whether`……

**这些词全部是停用词。** 按"实词 = 不在停用词表中的词"，它们会被划成虚词 → 中档自动补全、重档不扣分、永不进轻档挖空候选。

**后果：整个拼写容错规则（见下文）花大力气要抓的同音异形词能力，在默认档位上结构性失效——系统对最典型的连读弱读错误完全失明。**

所以：**高危同音组中的词一律计入关键词，无论是不是停用词。**

该表约 20-30 组，随仓库版本控制。它和下文明确拒绝的"易混词黑名单"不是一回事：那里要穷举所有可能听错的词对（永远列不全），这里只覆盖**高频功能词**的同音组——英语里这类组是封闭且稳定的，能列全。

## 四档强度

| 档位 | 用户操作 | 单句耗时 | accuracy |
|---|---|---|---|
| 🟢 保命档 | 听一句 → 点「懂/没懂」→ 看原文 | 5-8 秒 | **NULL** |
| 🔵 轻档（默认） | 挖掉 3-5 个词，只填空格 | 15-20 秒 | 考察词命中率 |
| 🟡 中档 | 只写考察词，**非考察词**自动补全 | 25-35 秒 | 考察词命中率 |
| 🔴 重档 | 全句完整听写 | 40-60 秒 | 考察词命中率（**非考察词写错不扣分**） |

⚠️ 中档的"自动补全"和重档的"不扣分"**只作用于非考察词**。考察词里的功能词（`their`/`its`/`than`）照常要写、照常扣分。

各档考察范围：

| 档位 | 考察词 |
|---|---|
| 保命档 | 空集 |
| 轻档 | 从候选池按优先级取 N 个 |
| 中/重档 | 候选池全部 |

## 为什么要统一口径

如果各档各自用"答对数 / 本档考察数"，**分母不可比**，会导致：

> 疲劳时切保命档 → 正确率接近 100% → 趋势曲线不降反升 → 自动升档把用户踢回重档 → 与保命档的设计意图正面冲突，形成档位震荡

**三条铁律**：

1. 保命档不参与任何正确率统计，只计 streak 和"没听懂的句子"清单
2. 趋势曲线**按档位分线**，不同档位的点不连成一条线
3. 升降档判定**只在同档位内累计**

**全局规则：`tested_words_total = 0` → `accuracy = NULL`**，不得写 0 或 100。

## 实词的定义

**不引入 POS 标注库。** "实词"用可执行的近似定义：

> 实词 = 不在停用词表中的词

停用词表是固定文件（119 词），随仓库版本控制。不要为词性精确引入 NLP 库——收益不抵复杂度。高危同音组就是这个近似的补丁。

⚠️ **这个定义只用于"挖空优先级"和"关键词预计算"，绝不用于决定中档的自动补全范围。** 中档补全的依据是**考察词 / 非考察词**。用停用词表决定补全范围会让 `their`/`its`/`than` 全被自动填上，上面堵住的失效通道原样回来。

## 挖空词选择（轻档）

从**候选词池**按优先级取前 N：

1. 该句中**已到期（`due <= today`）的历史错词** ← SRS 嵌入听写的机制，见 [srs.md](srs.md)
2. **该句中高危同音组的词** ← 刻意排在普通实词之前，这是要抓的核心错误类型
3. 该句中未到期的历史错词
4. 低频实词（**词频 rank > 3000**），rank 越大越优先
5. 其余实词

**N = min(5, max(1, round(候选池大小 × 0.4)))**

实际取值范围是 **1-5 而非 3-5**：池 ≤3 时 N=1，池 4-6 时 N=2，池 ≥13 才到 5。

- 候选池不足就有几个挖几个
- 候选池为空（如 "Yes, of course."）→ 降级为保命档形式呈现，`accuracy = NULL`

## 归一化流水线（顺序固定，不可调换）

1. 转小写
2. **弯撇号归一为直撇号**（`’`/`ʼ`/`′` → `'`）
3. **展开缩写**（白名单）：`don't→do not`、`doesn't`、`didn't`、`can't/cannot→can not`、`won't→will not`、`isn't`、`aren't`、`wasn't`、`weren't`、`gonna→going to`、`wanna→want to`
4. 连字符视为词边界（`well-known` → `well known`）
5. 去除**词首尾**标点（词内撇号保留）
6. 折叠连续空白
7. 按空白分词

实现见 [`src/shared/normalize.ts`](../../src/shared/normalize.ts)，与 [`tests/shared/normalize.test.ts`](../../tests/shared/normalize.test.ts) 一一对应。

### `'s` / `'re` / `'ve` / `'ll` 一律不展开

`it's` 与 `its`、`they're` 与 `their` 在听感上有真实差别，**正是四六级听力考点**。展开会让它们塌缩成同一串，等于放过了最该抓的错误。

归一化后 `it's ≠ its`——**这是期望行为，不是 bug。**

`n't` 类相反：`don't` 与 `do not` 连读中难以区分，transcript 写法也不稳定，判错属误伤，所以进白名单。

### 弯撇号归一必须排在展开缩写之前

BBC/VOA 的 transcript 用 `’`（U+2019），用户键盘打的是 `'`（U+0027）。白名单正则按直撇号写死，不先归一的话 `don't`（弯撇号）永远匹配不上，缩写展开在真实素材上直接失效——不是极端情况，是**主力素材源的默认书写**。

### 词首尾去标点顺带解决了弯引号包生词的问题

6 Minute English 每期都用弯引号包装当期生词（如 `‘bewildered’`），归一化第 2 步已把弯引号也转成直引号，第 5 步的"去词首尾标点"会把它们一起剥掉。**这一步不能只处理常见标点、漏掉引号**——漏掉的话生词 token 会带着引号变成 `'bewildered'`，永远无法和用户打的 `bewildered` 判等，白白把这批核心生词的听写判定废掉。

### 第 2 步必须是字符串级正则替换

不能等分词后逐 token 查白名单：分词前 `don't,`（带尾逗号）是一个 token，与白名单键 `don't` 不相等，查表完全匹配不上，**白名单等于失效**。

而第 3 步去标点又发生在展开之后，顺序不能调换（调换会导致 `it's → its`）。所以第 2 步只能用带词边界的正则在整句字符串上做。

## 拼写容错（第二个大坑）

**曾经的错误规则**：编辑距离 ≤1 一律视为拼写失误、不进错词库。

致命缺陷：`there`↔`their`、`than`↔`then`、`week`↔`weak`、`affect`↔`effect` 编辑距离都是 1，全被判成"手滑"排除掉——**而它们恰恰是系统存在的理由**。

**正确规则**：

> 编辑距离 ≤1 时，看**用户打出的串本身是不是合法英文单词**：
> - **是真词** → 判**错**（听成了别的词），进错词库
> - **不是任何英文词** → 判**拼写失误**，计入 accuracy 分子，**不**进错词库

| 原文 | 输入 | 判定 |
|---|---|---|
| their | there | ❌ 错（距离 2，且 `there` 是真词） |
| then | than | ❌ 错（距离 1，但 `than` 是真词） |
| receive | recieve | ⚠️ 手滑（相邻换位距离 1，且不是英文词） |

**距离用 Damerau-Levenshtein，含相邻换位。** 纯 Levenshtein 会把 `receive`/`recieve`、`believe`/`beleive`、`friend`/`freind` 记成 2 步——而相邻换位正是最常见的手滑类型，全判成"听错"就白费了。

需要一份**合法英文词表**（约 10 万词，SCOWL size-60 量级）。**没有它整条规则无法实现**，不是可选依赖。词表过大（如 37 万词的 `words_alpha`）会让生僻词也算真词，手滑被更多地误判成听错。

## 计分规则

| 情形 | 分子 | 分母 | 进错词库 |
|---|---|---|---|
| 完全正确 | ✅ | ✅ | ❌ |
| 拼写失误 | ✅ | ✅ | ❌ |
| 听成别的词 | ❌ | ✅ | ✅ |
| 漏写 | ❌ | ✅ | ✅ |
| 多写（原文没有） | — | ❌ | ❌ |

只有**考察词**参与计分。对齐用词级 LCS。

### 对齐算法的两个陷阱（第三个大坑）

LCS 回溯时有两处极易在"看起来是等价写法"的重构中踩坑：

1. **相同分数方向的平局必须严格取 `>`，不能写成 `>=`。** 写成 `>=` 会让 `expected` 一侧在任何一个 `actual` 词被推进候补队列之前就被消费掉，于是替换（听成别的词）永远配对不上对应的 `actual`，全部退化成 `missing`。**错词依旧会进错词库，只是判定分类从"听错"变成"漏写"，UI 上一切正常、什么都看不出来**——这是三处大坑里唯一一处不会露出任何外部症状的，只能靠单测按住。
2. **候补队列必须用 `shift()`（FIFO）消费，不能用 `pop()`（LIFO）。** 回溯方向是从句尾往句首走，候补里先入队的 `actual` 词在原句中的位置反而更靠后，所以要反着退出来对齐；用 `pop()` 会把连续两个写错的词的配对顺序整体颠倒。

这两条都没有独立的表层现象——错词计数、分母、`accuracy` 全部正常，只有具体到"哪个词配对成了哪个词"才能看出错，**必须靠对齐专项单测覆盖，不能靠肉眼看分数**。见 [`tests/shared/diff.test.ts`](../../tests/shared/diff.test.ts) 的"对齐的两个已知陷阱"用例。

## 分词细则

| 情况 | 规则 |
|---|---|
| 连字符词 | `well-known` ≡ `well known`：分词前把词内连字符替换为空格 |
| 数字与量词 | `£5m`/`2019` 与 `five million`/`twenty nineteen` 判等价（归一化时数字转英文读法）。实现成本过高时**把含数字的词排除出考察词**——绝不能让它当错词入库，那是格式差异不是听力问题 |

## 推进与中断

| 规则 | 说明 |
|---|---|
| **错 ≤1 个考察词即算过**，但**仅当 N ≥ 3** | **不用百分比阈值**：轻档典型只挖 3 个空，80% 等价于必须全对，反而比重档严苛。而 N ≤ 2 时"错 ≤1"必然判 `ok`，`weak` 在短句上永不触发——所以 N ≤ 2 要求全对 |
| 没过也放行，只标 `weak` | 不强制重听。强制重听就是死磕 |
| 听满 4 遍自动亮答案 | 防止单句耗掉整个 20 分钟 |
| 亮答案后**不再提交**，记 `revealed` | accuracy 记 0，正常计入分母 |
| `revealed` 句**只有该档实际考察的词**入错词库 | **不是"句中所有关键词"**。轻档其余实词是显示在屏幕上的，用户从未被要求产出。全入库会让一篇素材涌进几十个没考过的词，冲垮时间预算并污染高频错词 TOP 10 |
| `revealed` 句命中的 **due 词按 `Again`** 写入 `reviews` 并更新调度 | 见 [srs.md](srs.md)。不写的话，双重调度恰恰在最该记 `Again` 的句子上保留 |
| **`skipped`（Tab 跳过）**：`tested_words_total = 0`、`accuracy = NULL`、**不入错词库、不触发联动**、但**计入 `sentences_done`** | 与保命档同构。若记 0 分，频繁跳过会把用户自动降档；跳过是碎片时间下的正常行为，不该被惩罚 |
| 随时中断，下次接上次那句 | 断点存 `materials.current_sentence_idx`，任何档位推进都更新，**不依赖对 attempts 的反推** |

全键盘：空格重播 / Enter 提交 / Tab 跳过。变速 0.75x / 1.0x / 1.25x。

## 档位自动调节（M2 才接入）

**M1 是手动切档**（快捷键 `1`/`2`/`3`/`4`，档位存 `localStorage`）。自动调节要读 `daily.accuracy_by_mode_json`，而 `daily` 属于 M2，为 M1 硬凑一套日聚合等于把 M2 做掉一半。

`grading.ts` 的 `nextMode()` 和测试在 M1 就写好了，只是没有调用方——降档下限那条规则趁热记下来成本为零。下面的规则是 M2 接入时的依据：

- 默认轻档
- 判定**只在同档位内累计**：连续 3 个「该档位有记录的日子」正确率 >90% → 提示升档；<60% → 自动降档
- **保命档完全不参与判定**：既不计入"连续 3 天"，也不中断已累计的计数
- **自动降档的下限是轻档。保命档只能手动进入。**
- **升档是提示（需确认），降档是自动的** —— 增加负担要征得同意，减少负担应立即生效

降档下限这条不能省：若允许自动降到保命档，用户就再也升不回来了——保命档产不出正确率，永远凑不满升档条件。保命档是**疲劳时的手动逃生舱**，不是自动下坠的终点。
