# 使用者画像与硬约束

**这是整个项目所有设计决策的前提。读别的之前先读这个。**

如果丢掉这一页，后续开发几乎必然走偏——因为这个项目看起来像"四级备考 App"，实际上不是。

## 一个必须记住的事实

> **使用者去年考研英语二 72 分。**

由此推出的三件事：

| 事实 | 推论 |
|---|---|
| 考研英语二词汇要求约 5500 词，覆盖四级的 4500 词 | **词汇不是短板。任何"系统化背四级词表"的功能都是无效劳动** |
| 考研英语二阅读难度高于四级阅读 | **阅读不是短板。不要做阅读模块** |
| 考研英语二**不考听力** | **听力是唯一的真缺口**，也是唯一能同时喂给六级的投入 |

更精确的问题定位：使用者的听力问题**不是"不认识这个词"**（词汇量够），而是**"认识但听不出来"**——连读、弱读、语速。

这条区分决定了一个核心设计：生词卡片正面必须是**原音频里的那一句 + 播放按钮**，不是「单词 — 释义」。词表卡治不了这个病。

## 硬约束

| 约束 | 值 | 违反会怎样 |
|---|---|---|
| 形态 | **PC 端网页**（使用者原话"先做pc端"） | — |
| 录入成本 | **尽量零录入** | 任何需要每天手工填表的功能都会被弃用 |
| 每日时长 | **工作日 20-30 分钟，碎片时间** | 不能要求"一次做完一篇"；必须随时中断、下次接上 |
| 疲劳度 | 使用者明确反馈**"全句听写太累"** | 这是四档强度存在的唯一理由，不要以"简化"为名砍掉保命档 |
| 目标 | 2026 年 12 月四级，**之后还要考六级** | 不是一次性冲刺。素材和数据结构必须能复用到六级 |

## 使用者自述的三个痛点

按重要性：

1. **怕掉线** —— 某条线好几天没推进才发现
2. **记不住** —— 信息散在各处
3. **没反馈** —— 缺少进度可视化，坚持不下去

**明确未选**"抢时间 / 不知道此刻该干哪件"。所以本项目**不做**优先级调度、不做时间块规划、不做每日任务推荐。有人提这类需求时，先回来看这一条。

## 更大的背景

本项目是「个人工作台」的第一期。使用者同时并行五条线：备考四级、读研、上班、辅导孩子功课、养生。

范围被**主动收敛到四级一条线**（使用者原话"暂时只考虑四级的需求"）。其余四条线的扩展位见 [data-model.md](data-model.md) 的 `lane` 字段，但**第一期不要碰**。

## 一个尚未验证的假设

"听力是短板"这个判断是从"考研英语二不考听力 + 使用者说没底"**推出来的，不是实测**。

已建议使用者先做一套四级听力真题摸底。**如果摸底结果是听力也不差（200+/248），整个项目的重心需要重新评估**——可能应该直接转向六级准备。

在摸底结果出来前，这一页的核心判断都带着这个前提。
